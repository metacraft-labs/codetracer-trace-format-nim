# Codebase insights — codetracer-trace-format-nim

## M24a-1: steps.dat/steps.idx are now SPEC-canonical (Rust-reader-compatible)
- exec_stream.nim writes the SPEC layout (codetracer-trace-format-spec/
  seekable-zstd.md): steps.idx = [chunk_size:u32][offset:u64]... (NO
  total_events header/trailer); each steps.dat chunk's uncompressed payload is
  header-less (NO per-chunk u32 count). This is BYTE-COMPATIBLE with the Rust
  codetracer_trace_writer::step_stream writer / codetracer_trace_reader::
  step_stream_reader::StepStreamReader. Proof: tests/test_nim_step_stream_
  crossread.nim writes a Nim production bundle and shells the Rust test
  codetracer-trace-format/codetracer_trace_reader/tests/nim_step_stream_
  crossread.rs to read its steps.dat — decoded GLIs must match.
- multi_stream_writer.close() now sets has_step_stream (bit 9) in meta.dat
  (alongside has_call_stream). The FFI reader (new_trace_reader.nim
  ensureExecReader) selects framing by that flag: SET ⇒ SPEC reader, CLEAR ⇒
  legacy. initExecStreamReader takes `legacy: bool` (default false = SPEC).
- BACKWARD COMPAT: pre-M24a-1 Nim-v4 bundles never set has_step_stream, so they
  read via legacy framing automatically. The legacy reader path (per-chunk u32
  count + total_events trailer) is retained; tested by
  test_exec_stream_legacy_back_compat (hand-builds a legacy stream).
- In SPEC mode the reader recovers total_events like the Rust reader: decode the
  LAST chunk's record count, then (numChunks-1)*chunk_size + lastCount.
- Test harnesses that build a bundle by hand via initExecStreamWriter +
  writeMetaDat AND read it via the FFI reader MUST pass hasStepStream=true to
  writeMetaDat (otherwise the reader picks legacy and misparses the SPEC bytes).
  Done in test_new_trace_reader/test_reader_integration/test_reader_calls_events/
  test_cross_format/test_reader_ffi/bench_regression_suite.
- ct-print --json-events step output is UNCHANGED (the ct_print_full golden only
  flipped has_step_stream false→true; the step section is byte-identical). NOTE:
  test_ct_print_events_log_fallback caches its ct-print binary at
  /tmp/ctprint_build/ct-print and only rebuilds when src/codetracer_ct_print.nim
  is newer — editing a transitive dep (exec_stream.nim) leaves a STALE binary;
  rm -rf /tmp/ctprint_build before running it after such edits.

## M24a-3: events.dat/events.idx are now SPEC-canonical (Rust-reader-compatible)
- io_event_stream.nim writes the SPEC layout: events.idx = [chunk_size:u32]
  [offset:u64]... (NO total_events); each events.dat chunk's uncompressed payload
  is a concatenation of LENGTH-PREFIXED records (varint rec_len + rec_bytes).
  Each record is `u8 kind (EventLogKind ordinal), varint step_id, len+metadata,
  len+content` — byte-identical to the Rust event_stream::IoEventRecord::encode.
  BYTE-COMPATIBLE with codetracer_trace_reader::io_event_stream_reader::
  IoEventStreamReader. Proof: tests/test_nim_io_event_stream_crossread.nim shells
  the Rust test nim_io_event_stream_crossread.rs to read the Nim events.dat.
- The on-disk kind byte is the EventLogKind ordinal (same u8 as events.log), NOT
  the coarse 4-value IOEventKind. ioEventKindToOrdinal / ordinalToIOEventKind map
  between them and ROUND-TRIP every IOEventKind (stdout↔Write(0), stderr↔
  TraceLogEvent(12), file_op↔ReadFile(4), error↔Error(11)). The IOEvent type now
  also carries `metadata` (previously dropped on the multi-stream path).
- multi_stream_writer.close() now sets has_io_event_stream (bit 11) and flushes
  the events chunk. ensureIOEventReader selects framing by the flag: SET ⇒ SPEC,
  CLEAR ⇒ legacy `.off` VRT (pre-M24a-3 bundles: u8 IOEventKind, varint stepId,
  len+data, no metadata). initIOEventStreamReader takes `legacy: bool`.
- readEvent is now `var` (one-chunk decompression cache), like the value reader.
- The FFI ct_reader_event_fields STILL returns the coarse IOEventKind ordinal
  {0,1,2,3} (uint8(ev.kind)), so the db-backend's kind mapping is unchanged.
- Hand-built bundles read via the FFI reader MUST pass hasIoEventStream=true to
  writeMetaDat + flush the io writer (done in test_reader_integration/
  test_reader_calls_events/test_cross_format/test_multi_stream_integration).

## ct-print reader paths (IMPORTANT, M23e context)
- ct-print has TWO independent readers:
  * `NewTraceReader` (src/codetracer_trace_writer/new_trace_reader.nim) — the
    v4 "multi-stream" reader. It sources EVERY event from the SPLIT per-kind
    streams (steps.dat / calls.dat / values.dat / events.dat + the four
    interning tables paths/funcs/types/varnames). It NEVER reads events.log.
    Its accessors read the split .dat files UNCONDITIONALLY — they do NOT gate
    on the meta.dat has_*_stream flag bits (those flags are advisory capability
    markers only; M23a–d merely surfaced them in --meta-json/--full).
  * `TraceReader` (src/codetracer_trace_reader.nim) — the legacy v2/v3 reader
    that decodes the combined `events.log`. Used as the fallback in
    codetracer_ct_print.nim `main()`.
- The two readers emit DIFFERENT --json-events formats and are NOT byte-compatible:
  v4 = lowercase type tags (path/function/step/call/value/io) with step_index,
  entry_step/exit_step, call_key, depth, separate varname/type declarations;
  legacy = capitalized (Path/Function/Step/Call/Value/Return), flat, values
  keyed by variable_id. The reprobuild engine (ctfs_trace.nim) parses the
  LOWERCASE v4 format.

## Writers are mutually exclusive on the Nim side
- `MultiStreamTraceWriter` (multi_stream_writer.nim) writes split streams +
  meta.dat, NO events.log. It stamps only has_call_stream=true (not the other
  has_*_stream bits) even though it writes all the streams.
- Legacy `TraceWriter` (codetracer_trace_writer.nim) writes events.log +
  meta.dat + meta.json + paths.json, NO split streams.
- The canonical RUST writer (codetracer-trace-format/codetracer_trace_writer)
  ALWAYS writes events.log AND additively writes split streams when the
  recorder opts in — so a real Rust bundle carries BOTH (the transition format).

## M23e-1 routing fix (codetracer_ct_print.nim main())
- Before opening with the v4 reader, ct-print inspects the layout via
  container.hasInternalFile: if steps.dat is ABSENT but events.log is PRESENT,
  it routes to the legacy reader (preferSplit=false). Otherwise (split present,
  with or without events.log) it uses the v4 reader. Without this, an
  events.log-only bundle was opened by the v4 reader and produced an empty
  event array (lazy split readers found nothing).

## M34b: the nimble `test` task is GREEN (was 48 pass / 3 fail)
Running every `exec` line of the nimble `test` task independently on
x86_64-linux now gives pass=51 fail=0, and `just test` exits 0. The three red
gates M34 found were all hard-coded PERFORMANCE thresholds embedded in
correctness tests. What changed:

- src/codetracer_ctfs/chunk_cache.nim (NEW) — bounded LRU of *decompressed*
  chunk payloads, keyed by a dense chunkIdx->slot `seq[int32]` (no Table, no
  hashing), evicting by byte budget (`DefaultChunkCacheBytes` = 64 MiB, a cap
  not a reservation), with a per-slot metadata type `M` so a reader can cache
  derived per-chunk state next to the bytes. Protocol is find / acquire /
  commit: an uncommitted slot is the LRU victim, so a failed decompression
  leaves the cache untouched. Evicted slots go on a FREE LIST and are reused;
  do not "simplify" that away — an evicted slot is reachable from neither the
  key map nor the LRU list, so dropping it strands its payload buffer for the
  cache's lifetime and the byte budget stops bounding memory at all. The
  `cacheSlotCount <= 4` assertion in test_chunked_table_chunk_cache_is_correct
  is the regression guard (it reports 16 buffers for a 2.5-chunk budget if the
  free list is removed). `prepare()` resizes a slot WITHOUT zero-filling
  (`setLenUninit`) because the caller immediately overwrites it with a Zstd
  frame — `setLen`'s zero-fill is a per-element loop and in a debug build it
  cost MORE than the decompression it precedes.
  The pre-existing generic `ram_cache.LruCache` was not reused: it is keyed by
  a Table for sparse keys and its `get` COPIES the value out, which for a
  64 KiB chunk payload reintroduces most of the cost the cache removes.
- zstd_bindings.nim — `zstdDecompressShared` uses one thread-local reusable
  `ZSTD_DCtx` instead of `ZSTD_decompress`, which creates and destroys a
  context on every call.
- chunked_compressed_table.nim — `ChunkedCompressedTableReader` had a SINGLE
  last-chunk slot; on the benchmark's 245-chunk table a uniform random read
  pattern hit it ~0.4% of the time. Now uses ChunkCache. New public probes:
  `cacheHits` / `cacheMisses` / `residentChunks`, and an optional
  `cacheBytes` parameter on `initChunkedCompressedTableReader`.
  151-161 us -> 54.6 us median per lookup; a repeated read of a resident chunk
  is 0.35 us (was 155 us).
- exec_stream.nim — `ExecStreamReader.readEvent` was O(chunkSize): step records
  are variable-length varints, so reaching record k re-decoded records 0..k-1,
  and every inflation ALSO re-walked the whole chunk just to count its records.
  A per-chunk record-start table (`ExecChunkMeta.starts`) is now filled by that
  same count pass, so readEvent is O(1); the reader also uses ChunkCache
  instead of one slot. `bench_navigate_to_step`: 263-267 us -> 1.4 us.
  In legacy framing the record count comes from a u32 header, so the start
  table is built lazily on the first `readEvent` for that chunk.
  initExecStreamReader defaults to DefaultStreamChunkCacheBytes (8 MiB), NOT
  the 64 MiB table budget: ct-print and the bulk FFI accessors walk the step
  stream sequentially and an LRU keeps everything it sees up to its cap, so
  that cap is a floor on their peak RSS. Before M34b the reader held one
  decompressed chunk, so this is the one place the cache costs memory.
- sub_block_pool.nim — `expandPool` zeroed each new 4096-byte block TWICE
  (`setLen` zero-fills what it appends, then a hand-written scalar loop did it
  again) and `allocate` cleared each popped slot with a scalar byte loop.
  Both are single `zeroMem` calls now (`setLenUninit` + one `zeroMem` in
  expandPool). 216-226 K -> 573-740 K allocs/sec (569-646 K when re-sampled at
  load 127 — only ~14% over the 500 K gate, the thinnest margin of the two
  gates that stayed in `test`).
  DO NOT remove `expandPool`'s zeroing: namespace.nim serialises the WHOLE
  pool buffer, including never-allocated slots, into the container, so
  uninitialised bytes there would make container output nondeterministic.

The chunked-table 50 us per-lookup gate is the one that did NOT come green on
the reference host and its assertion (plus the 20M records/sec write-throughput
one next to it) moved VERBATIM into tests/bench_chunked_table.nim, which only
the `bench` task builds. Reason: 1000 uniform random lookups over 245 chunks
touch 240 distinct chunks, so 240 Zstd inflations of 64 KiB each are
compulsory however good the cache is; this host inflates one in 124-175 us
(86-92 us with the host quiet; `zstd -b3 -B65536` independently reports
494 MB/s quiet / 382 MB/s busy for the same data), i.e. 22-41 ms of the 50 ms
budget is spent inside libzstd before any reader code runs. This is a 2012-era
Xeon E5-2650 @ 2.0 GHz; a CPU doing 1.5-2 GB/s would spend 8-11 ms there.
The cache behaviour is asserted instead by
`test_chunked_table_chunk_cache_is_correct` (byte-identity of cold vs cached
reads, correctness across a chunk change, correctness under forced eviction) —
counters, not clocks. See Value-Origin-Tracking.milestones.org section M34b.

Be honest about what that move costs: .github/workflows/ci-reprobuild.yml runs
`just test` and nothing else, and repro.nim deliberately does not model
benchmarks, so NOTHING IN CI RUNS `just bench`. The 50000 and 20_000_000
thresholds are still asserted (verified: `nim c -d:release -r
tests/bench_chunked_table.nim` aborts with AssertionDefect at 54.8-57.3 us on
this host, 7 of 7 runs at load 101), but only when a human types `just bench`.
Also measured independently, with a standalone C harness linking libzstd and
touching no code from this repo: inflating those 240 frames costs 31-40 ms at
load 120 and ~22 ms with the host quiet, out of the 50 ms budget. So libzstd
is 62-80% of the budget when busy and ~43% when quiet — it dominates, but it
does NOT by itself exceed the gate. The gate is MARGINAL on this host, not
arithmetically impossible; the honest statement is that closing it would take
a change to how much gets inflated (sub-chunk/seekable access), not a faster
reader loop.

## A FOURTH marginal timing gate, not in M34b's scope: test_ram_cache
bench_ram_cache_hit_latency asserts `perReadNs < 1000` and measures 790-890 ns
on the reference host (10 consecutive samples at load 100), i.e. ~15% headroom.
Observed to flake once at 1122 ns during a per-command sweep; passed in every
completed `just test` run and on a re-run of that same command. Root cause if
it ever goes persistently red: `LruCache.get` returns `Option[V]` and therefore
COPIES the cached value on every hit; the benchmark caches a 4096-byte block,
so almost all of the ~830 ns is one alloc + 4 KiB memcpy + free per read. The
fix is a non-copying accessor, which is an API change to a type
cached_trace_reader.nim also uses — not a threshold change. This is the same
property that made ram_cache.LruCache unsuitable as the chunk-payload cache.
